# github-fit

**一个判断 GitHub 项目"值不值得我投入"的 Skill。**

它不回答"这个 Repo 是什么"，而是回答：

> **这个项目对我当前有什么价值、值得投入多少、下一步该怎么处理。**

---

## 它解决什么问题

收藏夹里堆着几十个 GitHub 链接，每一个看起来都不错，但真正用起来的很少。

常见的失效方式有三种：

- **看得懂，用不上** —— 读懂了 README，但和自己的真实任务没有接口。
- **很好，但重复** —— 现有工具已经能做，只是包装更新更酷。
- **该装，但不该现在装** —— 项目确实合适，但当前阶段投入产出不成比例。

优秀的项目不等于适合你；适合你不等于现在值得投入；能安装不等于应该安装。

`github-fit` 的作用是把一个 GitHub 链接收敛成**一个明确的处理动作**，而不是一段"看起来不错"的评价。

---

## 它输出什么

默认输出一张 **GitHub Fit Card**（保持简短，只保留影响判断的信息）：

| 字段 | 说明 |
|---|---|
| 一句话看懂 | 这个 Repo 实际是什么 |
| 为什么跟你有关 | 结合你的当前目的说明关系 |
| 主要价值 | 工具 / 方法 / 资产 / 组件 / 探索（情报仅条件触发） |
| 真实性 | 区分已验证事实、项目声明与未知项 |
| 任务覆盖 | 覆盖真实目标的哪些部分，没覆盖什么 |
| 与已有能力的关系 | 新增价值、重复能力，或可能替代什么 |
| 投入与风险 | 只写会影响当前决定的重要项 |
| 当前处理 | 8 种动作之一，必须明确 |
| 为什么 | 1–3 句解释 |
| 最小下一步 | 只做一件事的话，做什么 |

某个字段对当前 Repo 没有意义时直接省略，不为模板完整而制造信息。

---

## 8 种处理动作

评估必须落到其中一个，不允许用"很适合你""值得关注""建议尝试"这类模糊结论收尾。

| 动作 | 含义 |
|---|---|
| **跳过** | 当前没有足够价值，不继续投入 |
| **留作情报** | 不使用 Repo，但保留其中的市场、岗位或趋势信号 |
| **只学方法** | 不安装，只提取值得学习的方法、流程或结构 |
| **抽取组件** | 不采用整个 Repo，只拿其中有价值的部分 |
| **低成本试用** | 设计一个真实、低成本的小任务验证价值 |
| **改造成个人资产** | 值得基于它形成自己长期可复用的资产 |
| **正式纳入工作流** | 已有足够证据支持持续使用 |
| **深度调查** | 当前信息不足，但潜在价值足以支持进一步调查 |

每次评估最终应明确**一个主要处理动作**。这 8 个动作不是推荐等级，一个项目经常正确处理是"只学方法"或"跳过"，而不是"纳入工作流"。

---

## 判断流程

```
1. 先判断你为什么看它
   工具价值 / 方法价值 / 资产价值 / 组件价值 / 探索路线
   （情报价值仅条件触发，不作为默认检查项）
        ↓
2. Reality Check：它实际上做到了什么
   README 是线索，不是证据。按证据优先级核查。
        ↓
3. 比较"你已经有的是什么"
   新工具必须证明自己相比现有方案有足够增量价值
        ↓
4. 判断真实任务覆盖
   你真正要完成的是 A，这个 Repo 覆盖了 A 的哪一部分
        ↓
5. 计算真实投入成本
   安装 / 依赖 / 学习 / 每次使用 / 维护 / 迁移 / License / 隐私
        ↓
6. 落到 8 种动作之一 + 给出最小下一步
```

几个容易跳过的关键点：

- **第 1 步不急着套模板。** 能从上文判断时不要重复询问；只有当缺失信息会**实质改变最终动作**时才追问。
- **第 3 步必须做。** 孤立评价一个 Repo 很容易得出"值得一试"，但放进已有工具栈里往往发现是重复能力。
- **第 5 步不等于安全审计。** 检查深度与当前动作匹配：工具路线看安装维护成本，资产/组件路线看 License 与可修改性，情报路线看来源真实性。
- **License Gate。** 无 LICENSE、UNLICENSED 或许可证不明确时，提示复用风险，不建议直接复制改造；但不因此否定"只学方法"或"留作情报"。区分"复制现有实现"和"依据公开思想独立重新实现"。

## 证据原则

> **README is a claim, not proof.**

README 是项目对自己的描述，不自动等于真实能力。Stars 是流行度信号，不是适配度。

调查深度分两级：

- **Level 1（默认）** —— README、目录结构、核心文件、安装方式、依赖、License、维护状态。目标是用最低成本判断是否值得继续投入。
- **Level 2（必要时）** —— 核心源码、entry points、tests、可运行示例、config/manifest、CI、架构、Releases、Issues/PR、Maintenance（维护状态）、安全相关行为。仅在准备长期使用、准备改造、README 与实现存在明显疑问，或现有证据不足以支撑判断时进入。

证据优先级：

1. 实际可执行源码
2. Tests / 可运行示例
3. Config / manifest / CI
4. 技术文档
5. README / marketing claims

README 缺失或失真时不要直接下调项目价值——继续按上述优先级核查源码、tests、manifest、CI 等，README 只是入口，不是必需证据。

重要结论需要区分等级：**Confirmed / Strong inference / Weak inference / Unknown**。不要把 README 声明写成已验证事实。

## 怎么用（最简单）

**github-fit 是一个 Agent Skill。** 它需要先加载到**支持 Skill 的 Agent 环境**中才能使用——并非所有 Agent 环境都原生支持 Skill，请先确认你的环境是否支持。

加载完成后无需额外运行时依赖，也无需复杂配置，把 GitHub 链接丢进对话即可。

```
评估一下这个 Repo：https://github.com/<owner>/<repo>
```

带上下文会让判断更准，但不强制：

```
评估一下这个 Repo：https://github.com/<owner>/<repo>
我的目的：想找能长期用的内容生成模板
我现有：已有 Agent 和 Skill 体系，主要用对话式工具
```

**最好的用法是带一个真实任务**，而不是泛泛地问"这个项目怎么样"。因为整个 Skill 的核心判断是"它对你当前的真实任务覆盖了多少"，没有任务就没法判断覆盖度。

---

## 使用边界

- GitHub Fit Card 输出完成，本次评估即结束。
- 最小下一步可以是"无需行动"，不为了满足模板强行制造任务。
- 默认不追问"要不要我帮你安装 / 修改 / 起草 / 实现"。
- 除非明确要求，不自动开启衍生任务。
- 默认目标是**帮助做决定，而不是展示研究量**。不要每个链接都变成技术尽调报告。

## 版本

**v1.1** —— 基于 3 个真实 Repo 的实际使用验证迭代而来。三个案例分别暴露了不同层面的判断失误，也分别对应三种容易被忽略的价值路径：工具价值不足但方法可学、工具不采用但方法结构有价值、不直接复用代码但值得作为行业情报。相关脱敏案例见 [`examples/`](examples/)。

主要调整方向：把"要不要用"的二元判断，扩展成"工具 / 方法 / 资产 / 组件 / 情报"五条价值路径，并强制收敛到 8 种处理动作之一。
