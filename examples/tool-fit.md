# 案例 A｜工具价值不足，但方法可学

> 本案例为脱敏、泛化示例，不指向任何具体项目。

## 场景

用户在整理一批来源分散的网页内容，希望减少手工搬运。

看到一个 CLI 工具，主打"从网页批量抓取并结构化输出"。README 写得很漂亮：一行命令、开箱即用、支持几十种站点。

用户的第一反应是：*装一下试试。*

## 判断过程

**1. 为什么看它** —— 工具价值路线：希望直接用它完成内容抓取这一段。

**2. Reality Check** —— README 声称"开箱即用"，但检查 `package.json` 与源码后确认：

- 核心抓取依赖无头浏览器，需要另行安装运行时；
- 结构化环节调用第三方模型 API，需要自备 key 和额度；
- 站点适配靠社区维护的规则文件，覆盖度与实际站点分布有关，README 中的"支持几十种"是规则总数而非可用率。

结论等级：*Strong inference*（源码与 manifest 支持，未实际运行验证）。

**3. 与已有能力对比** —— 用户已有对话式 Agent 与浏览器自动化能力，可以直接完成抓取与结构化；工具带来的增量主要是"命令更短"，而不是"能力边界扩展"。

**4. 任务覆盖** —— 用户真正要完成的是"抓取 → 清洗 → 归档"。工具覆盖"抓取"这一环，且把"清洗"外包给了需要额外成本的模型调用。归档环节仍需自己处理。

**5. 投入成本** —— 安装运行时 + 配置 API key + 学习规则文件格式 + 承担站点适配失效的维护成本。对一个低频任务来说偏高。

但检查过程中发现两处值得留下的东西：

- 它的**输出 schema 设计**（把页面元素归成层级化的内容块，而不是平铺的 text/HTML 二选一）比用户当前做法更稳；
- 它的**失败重试与降级策略**（规则失效时回退到通用解析，并标记置信度）可以直接搬。

## 这个案例说明了什么

**"能用"和"值得用"是两件事。**

这个工具没有缺陷——它只是解决了一个用户已经有解的问题。如果只按"功能是否匹配任务"来判断，结论会是"可用，推荐试用"；把"用户已经有什么"加进来之后，结论变成"重复能力，不新增工具"。

同时，工具不采用不等于零收获。**方法价值可以脱离工具独立存在**，而这个工具的 schema 设计恰好是它最成熟的部分。

这类判断的价值不在"省了一次安装"，而在于避免把有限的注意力花在一次注定不会长期使用的能力迁移上。
