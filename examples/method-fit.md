# 案例 B｜工具不采用，但方法结构有价值

> 本案例为脱敏、泛化示例，不指向任何具体项目。

## 场景

用户正在搭一套自己的多 Agent 协作方式，遇到的问题是：任务一长，角色之间的交接就散——上下文丢、返工多、没人知道该在哪个环节叫停。

看到一个大热的 Agent 编排框架仓库：星标很高、文档齐全、示例丰富，社区讨论热度持续。

用户的判断是：*这大概就是标准答案，直接上。*

## 判断过程

**1. 为什么看它** —— 先是工具价值路线（想直接用），但真实诉求其实更偏资产价值（想形成自己长期可控的协作方式）。

**2. Reality Check** —— 检查 `examples/`、CI 和 releases 后确认：

- 框架确实有真实实现和可运行示例，不是纯文档项目；
- 但它要求把整条工作流写进自己的 DSL，Agent 定义、状态、工具调用都走框架抽象层；
- release 节奏很快，`CHANGELOG` 里存在多次破坏性变更，迁移说明本身就是一份不薄的文档；
- 核心抽象与某一家模型厂商的能力深度耦合。

结论等级：*Confirmed*（源码、示例、releases 均支持）。

**3. 与已有能力对比** —— 用户已经在用对话式 Agent + Skill 的方式做编排，虽然不够系统，但**完全在掌控范围内**，改一行就生效。换成框架意味着把控制权从"自己的约定"转移到"上游的抽象"。

**4. 任务覆盖** —— 用户真正要解决的问题是"交接不散"，具体是三个痛点：角色职责不清、交接物格式不统一、缺少强制评审点。框架覆盖了前两个（用它的角色定义和状态传递），但第三个取决于使用者自己怎么用，框架不强制。

**5. 投入成本** —— 学习 DSL + 重写现有流程 + 承担 breaking change 迁移 + 厂商耦合。相比"自己定义三条约定"，成本量级不同。

但抽查源码时发现了一个很干净的设计：

- **角色分工层**：每个角色只有一个明确的输入契约和输出契约，不共享隐式上下文；
- **交接物格式层**：角色之间只传结构化产物，不传自由文本；
- **评审门层**：关键节点定义明确的通过条件，不通过就退回，不允许"带着疑问往下走"。

这三层是**架构思想**，不是框架特性——用任何工具都能实现。

## 这个案例说明了什么

**热度高、文档全、星标多，都不构成采用理由。**

这个项目是认真做的，示例是能跑的，问题不在质量，而在**采用成本与控制权**：引入框架意味着把自己的流程交给别人的抽象节奏。当收益主要来自"它想清楚了几件事"，而不是"它替我运行了什么"时，正确动作是抽取那几件事，而不是引入整个运行时。

另一个关键是：**组件价值不需要 License 允许复制代码。** 这里抽取的是公开的架构模式和结构约定，可以依据其思想独立实现，与直接复制实现是两回事。

判断"该抽哪一层"的方法是问：去掉这个框架，这个设计还剩多少？剩得越多，越值得抽。
